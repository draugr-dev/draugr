**A run has one gate.** `--fail-on` and `--fail-on-priority` are two different questions about the same finding, and setting both is now refused instead of failing on either: a verdict with two possible reasons cannot be read back to the rule that produced it. `config.gate.failOn` is new, so a descriptor can finally state its severity threshold rather than leaving it to a flag every pipeline had to remember, and `config.gate.controls` requires it, because a per-control severity threshold under a priority gate is a rule nothing consults.
